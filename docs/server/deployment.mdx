---
title: "Deploy and recover safely"
---

Build with `npm ci && npm run build`. Use a restricted PostgreSQL role, encrypted storage, TLS database connections and a non-root service account. Expose the trusted host and sandbox listeners only through your configured TLS reverse proxy; both bind to loopback by default.

Set the exact `HAIP_ORIGIN`, a separate `HAIP_SANDBOX_ORIGIN` containing `{scope}`, signing-key and independently trusted manifest files, OIDC issuer/client settings and the database URL. Configure wildcard DNS/TLS for App origins and preserve Host routing. Do not put cookies on sandbox origins.

Production additionally requires an independently administered Azure Blob container, versioning, locked WORM retention, permanent safety legal holds and restricted conditional writers. `HAIP_ANCHOR_INDEPENDENT_ADMIN=true` records an operator assertion; it cannot prove RBAC separation. Real deployment validation remains required.

Bootstrap each new tenant offline with `node haip-server/dist/main.js --bootstrap`, then provision directory entries and routes through operator endpoints. Remove bootstrap credentials from routine configuration.

Every restart of an activated production generation requires offline recovery. Stop listeners and covered executors, preserve launch fences, run `--recover` with `HAIP_RECOVERY_TENANT`, a recovery operator and a fresh token. Recovery retires the old namespace in independent storage before changing the database, clears restored private material, disables old credentials and revokes old grants. Start the unused new generation, reprovision identities/routes and obtain fresh review for new occurrences. A matching checkpoint prefix never proves a missing tail was complete.

Use `node scripts/backup.mjs create|restore|prune PATH` with a separate 32-byte backup key file. Backups are authenticated and encrypted; restore accepts only an empty isolated database and leaves admission fenced. Prune at least daily, keeping backups for at most 30 days.

Versioned SQL migrations verify checksums and reject newer unknown histories. Rehearse upgrades and rollback against isolated restored data. Never downgrade to automatic approval or erase execution fences. The repository `OPERATIONS.md` is the full runbook; `deployment/` holds uninstalled configuration examples.

Migration 003 from earlier drafts blocks new requests for existing tenants until the next UTC day because deleted request counts cannot be reconstructed. Existing review, confirmation and outcome reporting continue. Subsequent daily counters survive audit cleanup and credential rotation. Retain historical public keys and their validity/revocation history indefinitely when they verify permanent recovery records.
