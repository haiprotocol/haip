---
title: "HAIP 2 \u2014 messaging"
---

HAIP 2 uses authenticated JSON over HTTPS. Request bodies must be uncompressed JSON; duplicate keys, invalid UTF-8, non-finite numbers and unsafe precision are rejected. Valid decimal responses are supported through RFC 8785 canonicalisation. Use strings where a schema needs greater precision.

Mutation endpoints use explicit idempotency keys where documented. Keep keys stable across transport retries and change them only for a new operation. A changed input under an old key is a conflict. Never treat a timeout as proof that an effect did not happen.

Poll `GET /v2/requests/{id}` for authoritative state. Poll signed events using `GET /v2/events?after=<cursor>`, durably handle the page and retain `next`. Registered producer webhooks are an optional at-least-once notification channel. They may arrive late, twice or out of order, so always fetch current status.

The initial review interface is a browser link. No WebSocket, SSE, binary-frame, inline foreign confirmation or JSON-RPC execution transport is required or advertised. Historic HAIP 1 transport instructions remain in the [archive](/archive/v1/index).
